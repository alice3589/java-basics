🎨 デザインパターン

先人たちが見つけた「よくある設計の定石」。オブジェクト指向（10〜16章）の知識を土台に、再利用しやすく変更に強い設計を学びます。GoF（Gang of Four）の代表的なパターンを、手を動かして理解しましょう。

27. デザインパターンとは

デザインパターンとは、ソフトウェア設計でくり返し現れる問題に対する「定番の解き方」に名前を付けたものです。1994年にGoF（4人組）が23個のパターンとしてまとめました。パターンを知っていると、設計の引き出しが増え、他の人と「ここはStrategyで」のように短い言葉で意図を共有できます。

すべての土台：インターフェースにプログラミングする

多くのパターンに共通する考え方が「具体的なクラスではなく、インターフェース（抽象）に依存する」ことです。下の例では、Main は Japanese や English という具体クラスを意識せず、Greeter という「約束」だけを使っています。だから新しい言語を足しても Main は変えずに済みます。

interface Greeter { String greet(); }
class Japanese implements Greeter { public String greet() { return "こんにちは"; } }
class English  implements Greeter { public String greet() { return "Hello"; } }

public class Main {
    public static void main(String[] args) {
        // 具体クラスに依存せず、Greeter という「約束」だけを使う
        Greeter[] greeters = { new Japanese(), new English() };
        for (Greeter g : greeters) {
            System.out.println(g.greet());
        }
    }
}

パターンの3つの分類

🏭生成に関するパターン

オブジェクトの作り方を工夫する。
例：Singleton・Factory Method・Builder

🧱構造に関するパターン

クラスやオブジェクトの組み合わせ方。
例：Adapter・Composite・Decorator

🔁振る舞いに関するパターン

処理の分担・連携のさせ方。
例：Iterator・Strategy・State・Visitor

💡 この章では代表的な8パターンを扱います。パターンは「暗記するもの」ではなく「困ったときに思い出す道具箱」。まずは「どんな問題を解くためのものか」をつかみましょう。

28. Iterator パターン

Iterator（反復子）は、集まり（コレクション）の中身を1つずつ順番に取り出す方法を、中の構造から切り離すパターンです。「次はある？(hasNext)」「次をちょうだい(next)」という共通の窓口を用意します。

Javaでは Iterable を実装すると、拡張for文（for-each）がそのまま使えるようになります。配列でもリストでも木構造でも、使う側は同じ書き方で走査できるのが利点です。

import java.util.Iterator;

class BookShelf implements Iterable<String> {
    private final String[] books;
    BookShelf(String... books) { this.books = books; }

    public Iterator<String> iterator() {       // 「次の要素」を返す係を用意
        return new Iterator<>() {
            private int i = 0;
            public boolean hasNext() { return i < books.length; }
            public String next()     { return books[i++]; }
        };
    }
}

public class Main {
    public static void main(String[] args) {
        BookShelf shelf = new BookShelf("Java入門", "デザインパターン", "アルゴリズム");
        for (String title : shelf) {           // Iterator のおかげで for-each が使える
            System.out.println(title);
        }
    }
}
💡 コレクション（18章）の List や Set がfor-eachで回せるのは、内部でIteratorパターンが使われているからです。

29. Adapter パターン

Adapter（適合）は、既にあるクラスを、別のインターフェースに合わせて使えるようにするパターンです。電源プラグの変換アダプタと同じ発想。「中身は使いたいが、形（インターフェース）が合わない」ときの橋渡しです。

既存の Celsius（摂氏）を変更せずに、クライアントが欲しい Fahrenheit（華氏）インターフェースに「適合」させています。

// 既存のクラス（変更できない想定）
class Celsius {
    private final double c;
    Celsius(double c) { this.c = c; }
    double getCelsius() { return c; }
}

// クライアントが欲しいインターフェース
interface Fahrenheit { double getFahrenheit(); }

// アダプタ：Celsius を Fahrenheit に「適合」させる
class TemperatureAdapter implements Fahrenheit {
    private final Celsius celsius;
    TemperatureAdapter(Celsius c) { this.celsius = c; }
    public double getFahrenheit() {
        return celsius.getCelsius() * 9 / 5 + 32;   // 既存の機能を変換して提供
    }
}

public class Main {
    public static void main(String[] args) {
        Fahrenheit f = new TemperatureAdapter(new Celsius(25));
        System.out.println(f.getFahrenheit());   // 77.0
    }
}
💡 ライブラリの古いクラスを新しいコードに合わせたいときや、外部APIを自分のアプリの型に揃えたいときに活躍します。

30. Template Method パターン ― サブクラスに任せる

Template Methodは、処理の「手順（骨組み）」を親クラスで固定し、具体的な中身だけをサブクラスに任せるパターンです。共通の流れはひとつにまとめ、変わる部分だけを差し替えます。

下の例では output() が手順（ヘッダ→本体→フッタ）を固定し、本体の printBody() だけをサブクラスが実装します。final を付けることで「手順は変えさせない」意図も表せます。

abstract class Report {
    // テンプレートメソッド：処理の骨組み（手順）を固定する
    final void output() {
        printHeader();
        printBody();      // 中身だけサブクラスに任せる
        printFooter();
    }
    void printHeader() { System.out.println("=== レポート ==="); }
    abstract void printBody();
    void printFooter() { System.out.println("=== 以上 ==="); }
}

class SalesReport extends Report {
    void printBody() { System.out.println("売上: 1,000,000円"); }
}

public class Main {
    public static void main(String[] args) {
        new SalesReport().output();
    }
}
💡 同じテーマの仲間に Factory Method パターンがあります。「どのインスタンスを作るか」をサブクラスに任せる作り方で、生成手順を共通化しつつ、作る対象だけを差し替えられます。

31. Singleton パターン ― インスタンスをつくる

Singletonは、あるクラスのインスタンスがプログラム全体でただ1つだけになることを保証するパターンです。設定情報・ログ・接続プールのように「いくつもあると困る」ものに使います。

コツは2つ。コンストラクタを private にして外から new できなくし、唯一の入口 getInstance() から同じ実体を返すことです。

class Config {
    private static final Config INSTANCE = new Config();  // 唯一の実体
    private int count = 0;
    private Config() {}                                   // コンストラクタを隠す
    static Config getInstance() { return INSTANCE; }      // 入口は1つだけ
    void add() { count++; }
    int getCount() { return count; }
}

public class Main {
    public static void main(String[] args) {
        Config a = Config.getInstance();
        Config b = Config.getInstance();
        System.out.println(a == b);        // true（常に同じ1個）
        a.add(); a.add(); b.add();
        System.out.println(b.getCount());  // 3（状態を共有している）
    }
}
⚠️ Singletonは便利ですが「どこからでも触れるグローバル変数」になりがちで、使いすぎると依存関係が見えにくくなります。本当に1つであるべきか、よく考えて使いましょう。
💡 同じ「インスタンスをつくる」仲間に Builder（複雑なオブジェクトを段階的に組み立てる）や Prototype（複製して作る）があります。

32. Strategy パターン ― 分けて考える

Strategy（戦略）は、アルゴリズム（やり方）を部品として差し替えられるようにするパターンです。「何をするか」を呼び出し側、「どうやるか」を戦略オブジェクトに分け、if 文の分岐ではなくオブジェクトの差し替えでふるまいを変えます。

interface Discount { int apply(int price); }
class NoDiscount   implements Discount { public int apply(int p) { return p; } }
class HalfDiscount implements Discount { public int apply(int p) { return p / 2; } }

public class Main {
    static int checkout(int price, Discount d) {   // 値引きの「やり方」を差し替えられる
        return d.apply(price);
    }
    public static void main(String[] args) {
        System.out.println(checkout(1000, new NoDiscount()));    // 1000
        System.out.println(checkout(1000, new HalfDiscount()));  // 500
    }
}
💡 新しい値引き（例：3割引）を足したくなっても、Discount を実装したクラスを増やすだけ。既存コードを書き換えずに拡張できます（開放閉鎖の原則）。ラムダ式（21章）を使うと戦略をさらに簡潔に書けます。

33. Composite パターン ― 同一視する

Composite（複合）は、「単体」と「容れ物」を同じ型として扱えるようにするパターンです。フォルダの中にファイルやフォルダが入る——という木構造を、再帰的に同じ操作で処理できます。

File200

File も Directory も同じ Entry 型なので、使う側は中身を気にせず size() を呼ぶだけ。Directory は子の size() を再帰的に合計します。

import java.util.ArrayList;
import java.util.List;

abstract class Entry { abstract int size(); }      // 共通の型

class File extends Entry {                          // 「葉」：単体
    private final int size;
    File(int size) { this.size = size; }
    int size() { return size; }
}

class Directory extends Entry {                     // 「枝」：容れ物
    private final List<Entry> children = new ArrayList<>();
    Directory add(Entry e) { children.add(e); return this; }
    int size() {                                    // 中身を再帰的に合計
        int total = 0;
        for (Entry e : children) total += e.size();
        return total;
    }
}

public class Main {
    public static void main(String[] args) {
        Directory root = new Directory();
        root.add(new File(100)).add(new File(200));
        Directory sub = new Directory();
        sub.add(new File(50));
        root.add(sub);
        System.out.println(root.size());   // 350（File も Directory も同じ size() で扱える）
    }
}
💡 似た仲間に Decorator パターンがあります。オブジェクトを「包んで」機能を少しずつ足していく方法で、こちらも「包むものと包まれるものを同一視」します。

34. Visitor パターン ― 構造を渡り歩く

Visitor（訪問者）は、データ構造（要素）と、それに対する処理（訪問者）を分離するパターンです。要素のクラスを変えずに、新しい処理を「訪問者」として後から追加できます。

各要素は accept(visitor) で訪問者を受け入れ、自分に合った visit を呼んでもらいます（ダブルディスパッチ）。下の例では、商品構造はそのままに「合計金額を計算する」処理を訪問者として持ち込んでいます。

interface Visitor {
    void visit(Book b);
    void visit(DVD d);
}
abstract class Item { abstract void accept(Visitor v); }
class Book extends Item {
    int price; Book(int p) { price = p; }
    void accept(Visitor v) { v.visit(this); }   // 自分の型に合った visit を呼ぶ
}
class DVD extends Item {
    int price; DVD(int p) { price = p; }
    void accept(Visitor v) { v.visit(this); }
}
class PriceVisitor implements Visitor {          // 「処理」を外から持ち込む
    int total = 0;
    public void visit(Book b) { total += b.price; }
    public void visit(DVD d)  { total += d.price * 2; }  // DVDは2倍で集計
}

public class Main {
    public static void main(String[] args) {
        Item[] items = { new Book(1000), new DVD(500), new Book(800) };
        PriceVisitor v = new PriceVisitor();
        for (Item it : items) it.accept(v);
        System.out.println(v.total);   // 1000 + 1000 + 800 = 2800
    }
}
💡 「構造を渡り歩く」仲間に Chain of Responsibility があります。処理できる担当者が見つかるまで、要求を次々と後ろの担当者へ渡していくパターンです。

35. State パターン ― 状態管理

State（状態）は、「状態」そのものをクラスにして、状態ごとのふるまいと遷移をオブジェクトに持たせるパターンです。if や switch の山になりがちな状態遷移を、すっきり整理できます。

信号機を例に。各状態（赤・緑・黄）が「自分の次はどれか」を知っているので、呼び出し側は next() を呼ぶだけです。

interface State { State next(); String name(); }   // 状態ごとに「次」を持つ
class Red    implements State { public State next() { return new Green();  } public String name() { return "赤"; } }
class Green  implements State { public State next() { return new Yellow(); } public String name() { return "緑"; } }
class Yellow implements State { public State next() { return new Red();    } public String name() { return "黄"; } }

public class Main {
    public static void main(String[] args) {
        State s = new Red();
        for (int i = 0; i < 4; i++) {
            System.out.println(s.name());
            s = s.next();           // if 文の山ではなく、状態オブジェクトが遷移を知っている
        }
    }
}
💡 同じ「状態管理」の仲間に、状態の変化を他のオブジェクトへ自動で知らせる Observer、ある時点の状態を保存して後で戻せる Memento があります。
